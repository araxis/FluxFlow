# Goal: move the remaining FluxFlow workflow components into portable plugins

Migrate every remaining shipped workflow component into an independently installable family plugin. A family is complete when installing its package supplies its runtime, designer definitions, configuration, documentation and applicable environment support; removal makes it unavailable for new work without damaging existing projects. A different UI host must be able to consume the same definitions without loading Studio, Razor, MudBlazor, a native driver or a running companion.

Use the existing FluxFlow plugin contract, installer and installed-plugin catalog. Serial, MQTT, RabbitMQ and NATS/JetStream are working references and regression cases. Do not introduce another framework, feature flags, a second catalog, or a runtime implementation that stays in the host. Do not modify Core or WFENG. This is a packaging and ownership migration, not a redesign of component behavior.

## Starting point and resume rule

Use [the frozen inventory and acceptance evidence](component-plugin-inventory.md) as the migration ledger. The original baseline was 21 components in eight families. Sources, Logging, Routing and filtering, Transformation and aggregation, and Flow control have passed their package lifecycle trials on both frameworks. At this checkpoint the designer still registers **7 built-in components across three families**. Resume with **HTTP**. Do not repeat a completed extraction or count the presence of a plugin project as proof that its packaged lifecycle works.

## 1. Reconcile the inventory before moving a family

Compare the ledger with current palette registrations in `Code/src/Authoring/FluxFlow.Authoring/Definitions/DesignerComponentRegistration.cs`. Cross-check them against configuration registrations, `WorkflowExecution.RegisterComponents`, the ASP.NET Core host integration, host-supplied registrations, Studio editors and sample projects. The palette alone does not reveal resources, optional hosts or dynamic ports.

Track one row per persisted component type: current owner, proposed package, ports and link shapes, related resources, editor and environment contributions, supported hosts, a pre-migration saved fixture, and the test that proves compatibility. Include runtime-only registrations and existing aliases if discovered. Distinguish host-supplied resources from installable nodes. Do not invent future components to fill gaps in the inventory.

## 2. Migrate in this order

Package names below are proposed boundaries. Component and resource type strings are existing contracts and must not be renamed. Complete one family, including the package lifecycle trial, before starting the next.

| Order / family | Existing component IDs and resources | Distinguishing acceptance check |
| --- | --- | --- |
| 1. Sources | `scheduler`, `source`, `dataGenerator` | Run an existing scheduled flow; check expected values, repeat delivery, cancellation, and no ticks from a stopped run. Preserve Source expression handling and Data Generator's function scope, locale and preview behavior. |
| 2. Logging | `logger`; resource `logging.otlp` | Run Scheduler → Logger from installed packages. Preserve host-supplied loggers as well as configured resources. Compare captured records through transport and display, including full exception details. Uninstalling the Logger node must not turn off Studio or engine diagnostics. |
| 3. Routing and filtering | `gate`, `router`, `changeFilter`, `deduplicate` | Verify Open/Close wiring, configured router destinations, selector expressions, change detection, duplicate suppression and retention. Reopen a saved router with multiple branches and conditional links. |
| 4. Transformation and aggregation | `mapper`, `reducer`, `batch` | Check preview against execution, JSON values and metadata, reducer state boundaries, and count/time/Stop batch behavior against the baseline. Preserve the saved mapper engine, including non-JSONata configurations. |
| 5. Flow control | `rateLimit`, `requestReply`, `retry` | Keep Request–Reply on the existing Rate Limit implementation. Preserve host-owned limiter references. Test bounded concurrency, reversed and late replies, ACK/NACK/Timeout/NotDispatched, retry attempt counts, and Stop while work drains. |
| 6. HTTP | `http.client`, `http.trigger`; resource also named `http.client` | Preserve the distinct node and resource registrations. Hosts retain ownership of listeners, TLS, middleware and authorization. Installing the plugin must not silently start a listener. |

| 8. Bluetooth LE | `ble.client`, `ble.notifications`, `ble.server`; resources `ble.peripheral`, `ble.adapter` | Preserve manual addresses/UUIDs, peripheral bindings, discovery cancellation, Visual/JSON GATT editing, descriptors, advertising, exact bytes, Notify/Indicate, bounded buffering, multi-service rollback and late callbacks. The shared expression editor, engine lookup, plugin function registry, graph, installer, Inspector renderer, log capture and execution lifecycle are platform services. They may stay in the host. Expressions, validators, function contributions, defaults and previews specific to a component belong to its plugin. Do not make a second copy of the expression engine or a family runtime to avoid an ownership decision. If a shared runtime primitive already lives in Core, reuse it without moving or changing Core.

## 3. Repeat this procedure for each family

1. **Capture the baseline.** Use an existing saved workflow from before extraction. Include real links, a changed property, relevant connection or host references, and an unknown JSON field. Record expected run outputs, errors and Stop behavior. Preserve the input fixture rather than regenerating it with the new package.
2. **Transfer ownership physically.** Put the implementation, registration, settings, portable design, documentation and package manifest together under `Code/src/Plugins/FluxFlow.Plugins.<Family>/`. Keep tests identifiable by family. Use ordinary project references: no linked source, shortcuts, duplicate code or empty forwarding projects. Keep a driver or platform-specific assembly separate from portable design only when it has a concrete purpose. Remove old registrations and host dependencies in the same slice; keep still-needed shared services available to other families.
3. **Reuse the design contract.** Supply palette entries, icons, ports, visibility rules, Property Grid groups, typed connection selectors, validation, help and optional Advanced JSON through portable definitions. Preserve missing references and manually entered values. Keep fields flat in the grid and use shared dialogs for complex editing. When an existing capability genuinely cannot be expressed (for example, a discovered GATT hierarchy), document the exact missing interaction, add the smallest reusable contract and renderer, and test both sides. Do not ship a family-specific Razor editor or a `switch` on a plugin type in Studio as a workaround.
4. **Wire execution and environment through existing APIs.** Use workflow and host registration hooks and the existing expression-function registration when needed. Move family-specific binding, provisioning and capability rules with their owner; keep shared host, networking and snapshot services generic. Preserve connection scope, manual fallback, effective configuration, credential references and locked snapshots. A missing package must not trigger hardware access, network traffic, project edits or an attempted run with a substitute component.
5. **Package and exercise the actual artifact on .NET 8 and .NET 10.** Use a clean temporary plugin store, project and companion. No source-project reference, developer-installed driver assembly or preloaded family registration may stand in for the package. Confirm the package follows the common folder/ZIP/local NuGet layout. Test its dependencies and design loading on both targets; build the portable design without a UI framework or runtime driver reference.
6. **Perform the lifecycle trial.** Install → open the original fixture → edit one property and one wire → Undo and Redo → save and reopen → run and Stop. Remove the plugin, applying the normal restart flow. Its palette entries, connection choices and runtime registrations must disappear. Open and save the project while the plugin is absent. Reinstall, reopen, Undo/Redo a fresh edit, run, Stop and rerun. Compare the complete saved project structurally at equivalent history points: IDs, port names, link endpoints and conditions, unknown settings, positions, colors, environment bindings and snapshots. Preserve actual Undo/Redo semantics; do not introduce a requirement to persist the undo stack across restarts.
7. **Close the slice with evidence.** Record package, targets, fixture, exact tests, observed behavior, and any unavailable external capability. Run the relevant log-contract tests when changing execution or logging, including the existing RabbitMQ shutdown and disconnect checks. Fix only demonstrated regressions. Do not start the next family with unexplained data loss, duplicate registrations, a broken packaged run, or an unreported verification gap.

For each family record the result separately for .NET 8 and .NET 10: package version, baseline project, actual host used, lifecycle result, behavior result, and any limitation. Distinguish an existing host limitation from a migration regression. If the unmodified host cannot run a scenario, retain that diagnostic and test the supported path on an appropriate host; do not expand runtime capabilities merely to make the migration trial pass.

## 4. Preserve the first-run experience and prove completion

- Deliver the intended basic components as ordinary preinstalled or bundled packages for a fresh Studio installation. Use the same loader and lifecycle as an explicitly installed package. Respect explicit removal after restart. Verify both an empty store and the default distribution; do not hide missing dependencies with hardcoded fallback registrations.
- Compare the inventory to installed manifests: every shipped component and owned resource has one owner; every public type ID and saved port still resolves as before. Check project references, published host outputs and runtime loading: the bare host and browser must not depend on family-specific implementations. Verify that removing one family leaves unrelated installed families usable.
- Run cross-family workflows from packages, including Scheduler → Logger, Retry → HTTP Client, and a migrated flow-control component with an already migrated broker plugin. Check original payloads, errors, telemetry, Stop retention and rerun isolation. Check the shared installer with a folder, ZIP and local NuGet source. Use isolated projects and stores; leave the user's tabs, installed plugins, credentials and devices alone.
- Finish with a coverage matrix for all 21 baseline components plus any additional shipped registrations found during inventory. Mark each result as verified, controlled-only, or blocked, with the reason. Build local artifacts; do not publish to a remote feed as part of this goal.
