# ROS 2 topic components

## Scope

Added the ROS component library and setup in the existing Configuration project:

- FluxFlow.Components.Ros2: RosPublisher<T>, RosSubscriber<T> and their options.
- FluxFlow.Configuration/Components/Ros2: node resources, DTOs and registration extensions.

Rcl.NET is pinned to 2.1.2, matching the existing ROS environment. Core and Application
remain independent of ROS. Configuration references the component library. Services and actions remain
subsequent steps; no parallel request/reply implementation was introduced.

## Component contract

Components borrow an IRclNode. Publisher converts each successful input value to a
generated ROS message and awaits native publication before forwarding its original
envelope. This confirms local publication only, not remote processing. Input errors
bypass publishing. Conversion/publish exceptions use ordinary processing errors.

Subscriber implements IFlowSource: it creates the subscription on Start, cancels
reading and disposes the endpoint on Stop. Each received message starts a new
envelope. Conversion failures produce error messages; native subscription failures
fault the source. Output and Events use native broadcasts with existing FlowLifetime.

Default conversion uses System.Text.Json with snake_case names and strict unknown
field rejection. Received values are snapshotted immediately. Byte arrays use Base64.
Options allow direct conversion delegates for custom FlowValue types. Generated ROS
bindings and native type-support libraries belong to the host.

Publisher disposal waits for in-flight native publication because Rcl.NET does not
accept a cancellation token for that operation. It cannot interrupt blocked native
middleware. DDS history, QoS and subscription queue policies remain native contracts;
this module does not add durable delivery.

## Configuration

AddRosNode registers deferred ros.node resources sharing a DI-owned IRclContext,
while respecting an existing host context. AddRosPublisher<T>/AddRosSubscriber<T>
associate configuration keys with compiled message types. Registration binds and
validates settings without constructing native resources. Build resolves resources;
Start begins receiving. Existing resource addressing, typed links, duplicate
suppression and Error/Events selection are reused.

Native PublisherOptions/SubscriptionOptions remain available in component options.
Configuration binds QosProfile and exposes the subscriber queue/drop settings.
There is no message catalog, assembly scan, custom transport interface or context
wrapper. Component endpoints are disposed before their borrowed node, and nodes
before the context through normal DI dependency ownership.

## Verification

- 30 ROS-specific unit test executions across .NET 8 and .NET 10: publishing,
  conversion, envelope preservation, lazy subscription, source failure, cancellation,
  disposal ordering, configuration snapshots, native QoS binding and duplicate links.
- Initial implementation completed verification of the 2,238-test solution suite.
- Setup was subsequently moved into Configuration/Components/Ros2 at the user's
  request. The separate configuration project/package is removed. Release planning
  retains two dependent package waves, and public APIs use the matching namespace.
- After the move, all 2,238 Release tests passed with no warnings. The isolated
  Configuration package consumer also passed on .NET 8 and .NET 10, resolving the
  ROS component dependency without requiring native ROS for non-ROS workflows.
- The runtime library and Configuration build and pack for .NET 8 and .NET 10.
- Isolated NuGet consumer on Ubuntu 24.04 / ROS Jazzy / .NET 10 exchanged Unicode
  std_msgs/String and nested geometry_msgs/Twist messages with independent Python
  ROS endpoints through subscriber-to-publisher workflows. Both round trips and
  graceful shutdown passed. No native .NET 8 ROS execution was performed.
- The upstream message generator emitted three nonfatal warnings when reading package
  Git revision metadata through LibGit2Sharp; generated messages compiled and native
  interoperation passed. The FluxFlow solution build reported no warnings.

Reproduce the packaged native check from Windows with a configured Jazzy WSL host:

```powershell
./eng/verify-ros2-consumer.ps1 -Distribution Ubuntu-24.04 -LinuxUser <user>
```

It builds an isolated candidate feed and consumer, sources /opt/ros/jazzy/setup.bash,
uses localhost discovery on domain 173 and unique /fluxflow_test_ topic names, and
verifies against rclpy. It requires .NET 10, ROS interfaces and rclpy in that WSL
distribution. Evidence is retained under the printed temporary directory.

No commit or publication was performed.
